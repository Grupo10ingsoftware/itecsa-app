# P13: configuración HTTP y evidencia de despliegue

## Controles comprobados en el repositorio

- Express establece `X-Content-Type-Options: nosniff` y `Referrer-Policy: no-referrer` antes de CORS, parsers, estáticos y rutas; `X-Powered-By` está desactivado. El proxy debe conservar esos headers sin emitir valores contradictorios.
- CORS anuncia únicamente `FRONTEND_ORIGIN`. Esto controla lectura desde navegadores, no acceso directo ni abuso. La API HTTP no sirve el HTML de la SPA según el código versionado.
- `express.json()` limita JSON a `100kb` por defecto. No hay una ruta multipart activa identificada. El payload de alta de pedido admite una observación de origen de hasta 16.000 caracteres; medir pedidos reales antes de reducir el límite. El límite de bytes, conexiones y tiempos para otros tipos de cuerpo corresponde al perímetro hasta que se defina una ruta que los necesite.
- Tras JWT e identidad local activa se aplican cuotas por usuario: 120 lecturas o 30 escrituras por minuto. Reset de contraseña y recuperación PIN tienen cuotas propias por IP/cuenta. Producción utiliza `SecurityThrottle` compartido en MySQL; desarrollo y pruebas usan memoria. La disponibilidad de la tabla en la BD de destino debe verificarse antes del despliegue.
- `/api/health/live` es público y no consulta BD; `/api/health/db` devuelve 404. `/internal/ready` está deshabilitado por defecto, requiere `X-Health-Token` cuando se habilita y consulta BD. Mantenerlo en red interna.
- Los errores del parser y las excepciones pasan por el handler global. Las respuestas 413 y 5xx no incluyen cuerpos de solicitud, stack ni detalles de dependencias; los eventos internos se correlacionan con `X-Request-Id`.

## Qué falta para cerrar P13

El repositorio no contiene la configuración efectiva del hosting de la SPA, reverse proxy, terminación TLS, reglas del borde ni orquestador. Tampoco da acceso al entorno productivo. Por eso las pruebas locales demuestran el comportamiento de Express, pero no los headers, límites ni rutas accesibles que recibe un cliente externo. Los siguientes puntos siguen **pendientes de evidencia del despliegue**; no se deben dar por implementados por este commit.

| Pendiente | Por qué no puede resolverse aún | Evidencia y criterio de cierre |
| --- | --- | --- |
| CSP de la SPA | Express no entrega el HTML de React según el código versionado. Se desconoce el servidor que lo entrega, el dominio final de API/Auth0 y los posibles orígenes de `profile.picture`. Una política restrictiva sin esos datos puede interrumpir login, callback o imágenes. | Identificar el servidor y los orígenes efectivos; instalar `Content-Security-Policy-Report-Only` en la respuesta HTML, revisar reportes y probar login/callback, llamadas API e imágenes. Pasar a bloqueo sólo con una política probada. La CSP en JSON de la API no sustituye este control. |
| HSTS y TLS | No consta dónde termina TLS ni si todos los accesos públicos usan HTTPS permanentemente. HSTS puede impedir acceso a un dominio que aún necesite HTTP. | Aportar configuración del punto TLS y comprobar desde fuera redirección HTTP→HTTPS y respuesta HTTPS. Configurar HSTS en el componente que entrega HTTPS; decidir `includeSubDomains` y `preload` sólo tras inventariar subdominios. |
| Headers en el borde | Las pruebas comprueban `nosniff` y referrer policy en Express, pero un proxy puede sobrescribirlos o servir la SPA con otra política. | Capturar headers de API y HTML en el dominio público para 200, 4xx y 5xx; confirmar un único propietario por header y ausencia de valores contradictorios. |
| Cuota anónima e IP confiable | Las cuotas existentes se aplican después de JWT/identidad, salvo reset. No hay evidencia de límites del borde para tokens inválidos, rutas desconocidas o sondas. `TRUST_PROXY=0` es sólo el ejemplo; no se conoce la cadena real de proxies. | Aportar topología, política de limpieza de `X-Forwarded-*`, número de instancias y reglas del borde. Probar cliente real y header IP falsificado. Si el borde carece de cuota, definir e implementar una compartida antes de autenticación, con excepciones medidas para health; comprobar 429, `Retry-After` y recuperación. No usar memoria como cuota global de producción. |
| Almacén de cuotas de producción | El código usa `SecurityThrottle` en MySQL, pero el repositorio no prueba que su migración esté aplicada a la base de destino. El runbook de despliegue indica que no se aplicó a la base compartida durante aquella entrega. | Verificar esquema/migraciones y permisos en el entorno objetivo con el procedimiento de despliegue aprobado; probar cuotas desde varias instancias y el comportamiento ante fallo de BD. No aplicar migraciones por esta documentación. |
| Health | No se identificaron consumidores, intervalos ni exposición de red de `/api/health/live` y `/internal/ready`. Cambiar rutas o cuotas sin ellos puede romper la orquestación; el token por sí solo no acredita aislamiento. | Registrar consumidor e intervalo de cada sonda; probar liveness público mínimo, readiness autorizado desde red interna, rechazo externo y fallo de BD. Mantener `/api/health/db` en 404. |
| Tamaño de cuerpo | El parser JSON rechaza más de `100kb`, pero no hay medición de los pedidos reales más grandes ni configuración del borde para otros tipos de cuerpo, bytes y tiempos. | Medir el mayor pedido legítimo sin registrar PII; probarlo bajo el límite y probar 413 por encima. Confirmar límites del proxy para tipos no JSON y solicitudes lentas antes de fijar excepciones. |
| Auth0 real | Los tests locales usan configuración sintética y no ejercitan el tenant, el navegador ni el callback desplegado. | Completar login y retorno a la SPA en el entorno autorizado, con CSP en observación y CORS del origen efectivo; conservar resultado sin tokens ni datos personales. |

Hasta completar estas comprobaciones, el estado correcto es **P13 parcialmente implementado; cierre pendiente del entorno**. Mantener `TRUST_PROXY=0` mientras no se valide el proxy y no tratar `req.ip` como IP final del usuario. Este documento no acredita configuración productiva ni amplía el alcance de P10, P12, P23 o P25.

## Evidencia local de esta rama

- `npm test` en `capaServidor`: 859 pruebas aprobadas, 2 omitidas, 0 fallidas. `test/p13.http.test.js` verifica respuestas HTTP reales: headers en 200/401/404/413/500, CORS y preflight, liveness, readiness sin token, JSON de 90 KB aceptado por el parser, JSON de 110 KB rechazado con 413, 429 con `Retry-After` y recuperación de ventana, IP con y sin proxy confiable, y 500 sin detalle interno.
- `npm test`, `npm run lint` y `npm run build` en `capaVista`: aprobados. Estas pruebas no sustituyen un login/callback real contra el tenant Auth0 ni una inspección del proxy público.
- Ejemplos del contrato local: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; el 413 devuelve `PAYLOAD_TOO_LARGE` y mensaje fijo, y el 429 devuelve `RATE_LIMITED` con `Retry-After`. `X-Request-Id` correlaciona el 500 con el evento de servidor sin incluir el mensaje original.
